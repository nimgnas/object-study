# 변경과 의존성

### 절차적인 설계의 단점

- 데이터를 구현한 코드의 수정에 취약하다
  - 데이터를 수정하면 프로세스도 수정해야 함

### 의존성

- 다른 코드가 수정될 때 함께 수정될 수 있는 `가능성`
- 어떤 클래스 안에 다른 클래스가 정의되어 있다면 의존성을 의미

### 추측에 의한 설계 전략

- 객체가 사용될 문맥을 고려하지 어떤 상황에서도 데이터를 사용 가능하도록 내부의 데이터를 그대로 드러내는 설계 방식
- 데이터가 변경될 때 함께 수정될 부분을 예측하고 제어하기 어려움

### 데이터와 프로세스의 분리가 원인

-

> **캡슐화의 이유와 getter, setter 데이터 접근 이유**
>
> - 외부에서 객체의 내부 데이터를 임의로 수정해 비정상적인 상태가 되는 것을 방지 (나이에 관한 데이터가 음수 값)
> - 유지보수과 변경에 유리, 외부 코드는 공개된 메서드에만 의존하게 되기 때문에 내부 로직을 변경해도 외부 코드를 고칠 필요가 없다.
> - get, set은 데이터에 접근 하기 전에 위와 같은 이유들로 검증의 역할
